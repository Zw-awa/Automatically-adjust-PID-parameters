# 模型为什么会这样给你调参

这份文档不教你改 prompt，只解释当前项目里模型大概依据什么来给建议。

## 1. 模型看到的不只是一个问题句子

每次调参时，项目会把这些信息一起给模型：

1. 当前控制环名称
2. 当前 `Kp/Ki/Kd`
3. 当前性能指标
4. 最近一段采样数据
5. 最近几轮调参历史
6. 目标要求

所以模型的建议并不是凭空猜，而是基于当前这一轮的实际表现。

## 2. 模型最看重哪些指标

最关键的是：

1. 超调量
2. 调节时间
3. 稳态误差
4. 振荡次数

可以这样理解：

1. 超调太大，通常说明系统太猛
2. 调节时间太长，通常说明系统太慢
3. 稳态误差太大，通常说明最后还没跟上目标
4. 振荡太多，通常说明参数偏激进

## 3. 为什么要把历史记录也给模型

因为如果只看当前一轮，模型很容易每次都改得太随意。

带上历史记录以后，模型更容易知道：

1. 哪个参数已经连续改了很多次
2. 哪个参数在来回震荡
3. 上一轮到底有没有改善

简单说，历史记录是为了减少“来回乱调”。

## 4. 为什么返回必须是结构化结果

因为项目还要继续拿模型的返回值做这些事：

1. 检查参数是否越界
2. 限制单次变化幅度
3. 显示给你看
4. 在线模式下发给设备

如果只是自然语言，很难稳定处理。

所以当前项目要求模型返回：

1. `kp`
2. `ki`
3. `kd`
4. `reason`
5. `confidence`
6. `expected_improvement`
7. `converged`

## 5. 为什么模型的建议不一定原样生效

因为模型只是给建议，不是最终执行者。

项目还会继续做本地限制，比如：

1. 单次变化不能太大
2. 不能超过配置里的上下限
3. 在线模式默认要你确认

所以即使模型给了比较激进的值，最终真正被应用的也会更保守。

## 6. 如果模型建议看起来一直不靠谱，通常先查什么

最常见的是下面几类原因：

1. 原始数据质量差
2. 样本数量太少
3. 目标要求太严格
4. 控制环名字和真实场景不匹配
5. API key 或模型调用本身不稳定

这时候最好的做法不是立刻怀疑整个项目，而是先拆开来看：

1. 先看离线分析指标是否合理
2. 再看仿真模式是否稳定
3. 最后再看在线模式和硬件链路

## 7. 这份说明能帮你做什么

它不是让你改代码，而是帮助你判断：

1. 模型这次给的建议有没有基本道理
2. 当前问题更像是数据问题还是调参问题
3. 你是不是应该先回头检查采样和协议，而不是继续盲调
